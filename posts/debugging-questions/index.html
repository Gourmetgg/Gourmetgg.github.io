debugging is mostly asking better questions

from “it is broken” to something you can test

06 November 20251 min read[ programming, learning ]

“It is broken” is an accurate observation, but a difficult place to start. There is too much world inside that sentence. A useful debugging session makes the sentence smaller.

Does it fail every time? Does it fail with the same input? Does it fail before the network request, or after it? Each answer removes a little uncertainty.

find the first surprise

I try to follow the data until I reach the first point where reality differs from expectation. Not the loudest error, necessarily. The earliest surprising value.

A missing field near the beginning can become a strange display near the end. Fixing the display might hide the symptom. Finding the missing field explains it.

change one thing

When possible, change one thing at a time. If three changes make a problem disappear, you have a working program and an unanswered question. Sometimes that is enough for the moment. It is rarely enough for confidence.

The nicest fixes come with a short explanation: this input reached this branch, this assumption was false, and this change handles it.

Debugging is not always tidy. But a better question usually makes the next ten minutes better.
